## 1. Результат версии и границы работы

Заказчик утверждает цель, ограничения, критерии готовности, бюджет и полномочия. Один тимлид принимает заказ и самостоятельно доводит его до готового результата: строит план, назначает исполнителей, решает технические вопросы, проверяет работу и возвращает итоговый отчёт. Промежуточные сообщения сообщают о ходе работы; обычные технические решения не требуют ответа заказчика.

Главные критерии 3.0: завершённый утверждённый заказ; отсутствие незапрошенных функций; отсутствие обычных промежуточных согласований; проверяемое качество; конечный процесс без циклов улучшений и review-of-review. Невозможность завершения сообщается честно с конкретным внешним блокером или исчерпанным лимитом.

В реализацию входят управляющий цикл, полномочия, назначение моделей, применимые проверки, согласованные активные skills и поставка новой версии. Не входят новая БД, очередь, сервис классификации, dashboard, общая платформа доверия, полное переписывание всех инструментов, дополнительные модели, очистка старых результатов, автоматический exploit, production deploy или изменение пользовательских credentials. Установка в рабочий Hermes — отдельный финальный этап с конкретной областью и разрешением.

## 3. Граница 3.0: что сохраняем и что прекращаем

**Новая версия — единый новый процесс на проверенных существующих механизмах.** Меняем управляющие решения в текущем runner на отдельной ветке; не строим второй конкурирующий runner и не поддерживаем две политики для новых заказов.

| Область | Решение для 3.0 |
| --- | --- |
| Активные роли | Функциональные имена: тимлид, инженер, архитектор, дизайнер, reviewer, применимый специалист. CENTURION — бренд; римские aliases допустимы в отображении, но не задают полномочий |
| Состояние заказа | Один controller-owned mission state; существующие order/result, ledger и execution events используются по назначению. Не создавать вторую изменяемую копию одного состояния |
| Старые orders/results | Не переписывать, не принимать заново, не переводить автоматически в 3.0. Новый runtime отклоняет попытку продолжить старый заказ как новый; незавершённый заказ сначала явно завершается/останавливается в прежнем режиме либо получает новый согласованный заказ с явным переносом результатов |
| Формат обмена | Сохранить проверенный V1 wire format там, где он достаточен. Явная `policyVersion: "3.0"` в controller-owned context обязательна для новых миссий и связывается с mission state; значение из текста исполнителя не авторизует новую политику. Отсутствие/неизвестная версия не включает скрытый legacy fallback |
| Совместимость | Старые артефакты доступны для чтения. Старые модели, команды, aliases и специальные пути не становятся обязательной поддержкой активного 3.0. Сохранение общего wire parser не означает сохранение старых разрешений |
| Обязательные церемонии | Убрать глобальные WAR ROOM, tribunal, review-of-review, согласование каждого файла и ровно две попытки на любой заказ |
| Полезные механизмы | Сохранить проверку identity/artifact, preflight, фактического diff, необходимых proof, create-only исходных результатов и независимости автора/reviewer |
| Установки и откат | До отдельного внедрения активная 2.6 не меняется. Откат восстанавливает проверенный набор файлов/config и не возобновляет неизвестные процессы или неподтверждённые побочные эффекты |

В рабочей копии сохранены девять исходных изменений runner/preflight/detector/blocker/schema. Их не считать принятыми автоматически. В N1 каждому назначается решение: переиспользовать после focused proof, адаптировать либо оставить вне поставки. Design-only trust schema не входит в минимальную 3.0. Ничего из этих исходных файлов не удаляется при фиксации плана.

Версии различаются: **product 3.0.0** обозначает релиз, **policyVersion 3.0** — применяемые полномочия и routing, **stateVersion** — форму сохраняемого controller state, **kit version** — совместимость устанавливаемого пакета. Существующие order/result V1 не обязаны менять номер. Несовместимое обязательное поле, новый формат state или изменение authority/acceptance требуют явного перехода; багфикс не даёт старому order новых прав. Старый runtime может не понимать новый metadata: поэтому 3.0 dispatcher проверяет объявленную capability runtime до передачи заказа, а не надеется, что старый бинарник сам его отвергнет. Upgrade/rollback fixture проверяет эту границу.

### 3.2. Один контракт и туннель исполнителей

Новые миссии: Hermes native loop как среда тимлида → существующий controller/Gateway → ограниченные процессы Codex CLI или Claude CLI → controller acceptance. Единственный active вход — `AGENT_ORDER_JSON_V1`, выход — `AGENT_RESULT_JSON_V1`, адресация — exact `AGENT_HANDOFF_V1`. `LEGION_ORDER_V1`, `CLAUDE_ORDER_V1` и старые results остаются историей/compatibility вне нового dispatch; автоматический перевод старого заказа запрещён. `Aquila` сохраняется техническим controller id V1, функциональное имя — тимлид. Новая иерархия не возникает из display alias.

Поля V1 сохраняют имена и обязательность: `outputContract.resultVersion/resultPath`, массивы result, `filesChanged` как объекты. Mission/task/product-attempt связываются в одном controller state и существующих context/routing metadata; новый обязательный `attemptId` в авторском result не вводится. N1 фиксирует точное отображение. Reviewer возвращает тот же envelope с **`executorExtensions.review`**, обязательным для 3.0 review orders и их native projection: `verdict` (`pass|fail|blocked`), `findings` (array), `reviewedOrderId`, `reviewedResultSha256`, `productSnapshotSha256`. Findings связываются с критерием и evidence; hashes контроллер сверяет со своим snapshot. `status=done` означает завершённое ревью, verdict `fail` — обнаруженный дефект. Нет verdict/binding → protocol failure без product replay; подтверждённый pass требует обоих уровней. Базовый V1 не получает обязательных review-полей для обычной реализации.

Транспорт — argv + stdin/файлы + раздельные stdout/stderr, без shell interpolation текста поручения. Codex: final candidate через `--output-last-message`, native schema через проверенный `--output-schema`, events отдельно. Claude: извлечение `structured_output` из native wrapper либо `result` из заранее выбранного text mode; две противоречащие формы отвергаются. Hermes JSONL при автоматизированном запуске самого тимлида позволяет наблюдать terminal `result`; он не добавляет третий worker в active routing. Native schema — проверенная projection единого canonical source; при несовместимости provider допустим заранее проверенный file-candidate mode, без повтора уже выполненной работы.

Adapter сохраняет полный raw wrapper/stream, фиксирует extraction field/event/version/hash в существующей closure/evidence и передаёт один candidate общему strict parser/builder. Progress, init, exit0 и `done` не являются приёмкой. Requested model/effort отделены от observed runtime evidence; отсутствие наблюдения не превращается в доказательство. Один чистый JSON fence допустим; произвольная проза, duplicate keys, смешанные documents и несовпадающий orderId отвергаются. Controller metadata не подставляется внутрь авторского результата, raw и finalized bytes не перезаписываются.

Внешний handoff идёт только через контроллер и проверенные `inputResults`/product snapshots. Исполнитель не назначает коллег. Hermes native `delegate_task` не входит в product launch первой 3.0: его permissive parsing и correction в том же child loop не обеспечивают требуемый no-write режим. Готовый optional Hermes → Codex app-server мост изучен, но смена agent loop/config и MCP projections не входит в core. MCP/ACP/serve/kanban не становятся новой очередью или вторым controller. При дальнейшем включении транспорта контракт остаётся тем же.

В первой 3.0 **новый child launch выполняет только Gateway**. Direct runner сохраняется для общей валидации, чтения/проверки и исторических fixtures; попытка direct-dispatch с policy 3.0 отвергается до spawn. Это исключает второй путь исполнения с другими timeout/custody правилами и не требует переписывать прежние артефакты.

## 4. Полномочия и единый рабочий цикл

```text
Заказчик: цель, критерии, бюджет, доступ и внешние действия
    ↓
Тимлид: план → поручение → результат → проверка → приёмка → итоговый отчёт
    ├─ исполнитель с необходимыми skills
    ├─ отдельный аналитик/дизайнер по конкретной необходимости
    └─ независимый reviewer по риску и пробелу доказательств

Программный controller обеспечивает состояние, границы, запуск и учёт доказательств.
```

Тимлид может менять декомпозицию, порядок, модель в разрешённой матрице, технический способ и необходимые локальные файлы/тесты внутри утверждённой области. Исполнитель не расширяет своё поручение и не делегирует дальше без назначения. Reviewer сообщает findings тимлиду, не правит продукт, не ослабляет критерии и не назначает другого reviewer.

Заказчик нужен только для существенно неразрешимой неопределённости цели, расширения полномочий/бюджета либо требуемого внешнего решения. Новая функция продукта, платёж, production deploy, секрет, изменение аутентификации, необратимая операция или публикация не становятся разрешёнными из-за общего слова «автономно». Если соответствующее действие уже явно согласовано и технически поддержано, повторный вопрос ради той же авторизации не нужен. Действующий V3 остаётся закрытым без необходимого проверяемого разрешения; создание такого verifier не является предпосылкой обычной локальной разработки 3.0.

При приёме заказа тимлид записывает ссылку на конкретное решение заказчика и его границы: цель/non-goals, продуктовые критерии, разрешённые среды/пути, классы действий и лимиты. Контроллер связывает этот снимок с mission ID/policy и проверяет перед dispatch. Текст исполнителя «заказчик разрешил» или наличие одного `policyVersion` не являются разрешением. Если для чувствительного действия нужен trusted verifier, обычная ссылка на разговор его не заменяет.

Примеры: новый файл контроллера и focused test для заказанного endpoint — техническая декомпозиция; новый endpoint, несовместимый API-контракт или новая платная зависимость — изменение заказа/полномочий. Тимлид выбирает локальный способ в принятом стеке; замена согласованного языка/платформы не разрешается по умолчанию. Новый helper допустим только при технической необходимости для исходного результата, а не по общей привычке skill.

Дефект и неполное исполнение одинаково требуют коррекции, если нарушен утверждённый критерий или необходимый инвариант заказанного поведения. Edge case не обязан быть перечислен буквально: например, обработка разрешённых входов — часть корректности endpoint. Новый сценарий продукта сверх цели остаётся предложением. Классификацию делает тимлид по доказательствам; нельзя требовать новых функций под видом качества или отвергать реальный дефект только из-за отсутствия его буквального названия в брифе.

### Состояние и завершение

Состояния миссии: `ready → running → verifying → completed`; коррекция возвращает в `running`, ожидание необходимого внешнего решения — `blocked`, исчерпание лимита/невосстановимый отказ — `failed`, а явная остановка владельцем без автоматического продолжения — терминальное `stopped`. Успех одного поручения не завершает миссию. Переход в `completed` требует закрытых критериев, действительных proof, контроллерской приёмки и отсутствия незавершённого процесса с неизвестным эффектом. Для V0 достаточно focused proof + self-review + контроллерской приёмки, без независимого reviewer; для V1–V3 дополнительно требуется применимое независимое ревью и gate по §5. `stopped`, `failed` и `completed` не возвращаются в `ready` автоматически. Это состояния миссии; исходные result-статусы `done|blocked|failed` и старые артефакты не переименовываются.

Существующий `execution_state.py` — **read-only projection из order/result/receipts**, а не хранилище событий или владелец миссии. Изменяемое состояние принадлежит controller в `agent_contract_runner.py`; переиспользуются `loopContract.statePath`, `LoopStateLock` и `atomic_write_loop_state`. В N1 выбранный файл состояния расширяется необходимыми mission metadata, а projection остаётся производной. Минимально требуются: mission ID, policy/state version, ссылка на утверждение, цель/non-goals, критерии, разрешённые действия/пути, лимиты, задания и зависимости, attempts, evidence, acceptance. Детальная JSON-форма фиксируется N1 внутри этого единственного источника; новая БД и дублирующая изменяемая mission state запрещены. Ledger — журнал наблюдений, не второй центр выдачи полномочий.

Перед побочным действием записываются intent и идентификатор попытки; после — наблюдаемый результат. При восстановлении сначала выясняется состояние уже запущенного процесса. Неизвестный внешний эффект не повторяется автоматически. Новый order ID, смена модели, reviewer или restart не сбрасывают mission budget.

Плановая политика локального пилота: общий лимит 45 минут, до 8 модельных запусков на миссию, включая консультации/ревью/повторы; до 3 продуктовых попыток на один ограниченный task. Каждый controller dispatch или отдельная correction turn учитываются до запуска, включая неуспешный вызов; retry/restart не бесплатен. **Запуск агента не равен одному provider API request:** внутри CLI есть tool turns и retry. Их API calls/tokens фиксируются отдельно по доступной telemetry; без enforcement нельзя заявлять лимит восьми фактических API requests. Native correction учитывается резервированием запуска, либо отключается/путь не включается; доступные iteration/retry limits и общий deadline ограничивают внутренний loop. Проверка статуса уже запущенного процесса не считается новым модельным запуском, но время продолжает учитываться. После двух последовательных одинаковых блокеров без новых доказательств прежняя стратегия прекращается. Тимлид может один раз сменить подход в остатке лимита; повышение лимита только через прежнюю authority boundary. Эти значения — стартовая проверяемая настройка пилота, не обещание достаточности для любого проекта; реальный заказ фиксирует лимиты при приёме. При неизвестной денежной стоимости действует лимит времени/запусков, cost=`unmeasured`; фиктивный денежный cap не заявляется.

Прогресс — закрытый критерий, новый проверенный результат либо устранённый конкретный дефект. Новый отчёт/hash/роль сам по себе не прогресс. Повтор допускается с конкретной причиной и ожидаемым новым свидетельством.

Сборкой результатов владеет тимлид. Зависимое поручение получает принятый вход с конкретной ревизией; непересекающиеся файлы сами по себе не доказывают независимость API/данных. Общие файлы и интеграция имеют одного назначенного writer. После объединения срезов проверяются затронутые критерии на итоговом snapshot; pass отдельных поручений не заменяет работоспособность их сочетания. Новый полный reviewer не добавляется: существующий применимый review привязывается к итоговому кандидату, неизменные доказательства переиспользуются. Итог заказчику содержит результат, путь/ревизию готового проекта, способ запуска в согласованной среде, проверенные критерии и реальные ограничения. Отчёт строится из acceptance; ошибка доставки отчёта не возобновляет разработку.

После compaction, новой сессии или потери памяти тимлид сначала перечитывает authority, открытые критерии, принятые результаты, intent/process state и остаток бюджета из единственного controller state. Summary, memory и ответы исполнителя не заменяют эти данные и не дают новых полномочий. Принятые шаги не повторяются; существующее согласование не запрашивается снова без изменения его границ. Повреждённый/недоступный state не создаётся заново с нулевыми счётчиками.

Deadline ограничивает исполнение, proof, review и завершение. N1 фиксирует, инженер в N4 реализует **резерв 30 секунд на остановку/финальную запись внутри исходного wall budget**, не сверх 45 минут/5 часов. Work cutoff = deadline − 30 секунд; child/proof/review timeout не больше остатка до cutoff, после него новые inference и proof запрещены. На SIGTERM отводится до 10 секунд, затем SIGKILL при необходимости; drain/сохранение исхода используют остаток общего 30-секундного резерва, не новый grace на каждый процесс. Явная отмена сразу закрывает dispatch и включает тот же bounded termination только для связанных процессов. Истёк резерв, процесс не подтверждённо завершён или запись невозможна → incomplete/unknown effect без acceptance/replay. Локальная остановка не доказывает отмены вычислений удалённым provider. Модельные ходы Hermes-тимлида видны отдельно от worker launches и ограничены тем же deadline и доступным native turn limit; восемь worker launches не являются лимитом всей inference тимлида.

## 5. Модели, роли и проверка

Канонические идентификаторы для routing/launcher: **Sol = `gpt-6.1-sol`, Luna = `gpt-6-luna`, Astra = `gpt-6-astra`, Opus = `claude-opus-5-5`**. Далее краткие имена используются только для чтения; строковые проверки и API используют эти точные IDs. `gpt-6-sol` — исторический ID, не alias текущего Sol и не активный fallback 3.0.

| Работа | Исходный маршрут 3.0 | Ограничения |
| --- | --- | --- |
| Тимлид | `gpt-6.1-sol` `high`, `xhigh` для трудных решений | Один владелец заказа; не подменяет независимую проверку собственного результата |
| Узкая механическая работа | `gpt-6-luna` `high`; `xhigh` при оправданной необходимости | Только `high/xhigh`; default `high`; ясный oracle и низкая неоднозначность. Повышение сложности переводит к Sol, не только увеличивает effort |
| Обычная реализация | `gpt-6.1-sol` `medium/high`; сложная — `high/xhigh` | `low` допускается только для механического случая, не как скрытая замена Luna или снижение review floor |
| Сложная архитектура, анализ, диагностика | `gpt-6-astra` `high` напрямую по задаче; `xhigh` для сложных/рискованных выводов | Отдельное read-only заключение; не обязательный этап и не терминальный reviewer. В первой 3.0 `medium` не включается: допустимы только `high` и `xhigh` |
| Визуальный дизайн | `claude-opus-5-5` `high` | Для первой 3.0 — ограниченный низкорисковый дизайн по фиксированному брифу, с допустимой V1-проверкой `gpt-6.1-sol`. Если фактический риск/неопределённость требует V2/V3, маршрут Opus не объявляется доступным без независимого gate; нельзя понижать классификацию ради запуска |
| Независимое ревью реализации Sol/Luna | `claude-opus-5-5` `high`; выше — по конкретному риску | Отдельная сессия и исходные доказательства; неизменный результат не отправлять на повторное полное ревью |
| Проверка низкорискового материала Opus | `gpt-6.1-sol` `high/xhigh` в отдельном запуске для автора `executor=claude`, `model=claude-opus-5-5`, при допустимом V1 | Не открывать обход medium/high-risk gate. Реализация Opus с обязательным V2/V3 остаётся вне первой 3.0 до отдельного доказанного независимого маршрута |

Предпочтение Opus для дизайна не означает запрет Sol на UI. Если UI требует
V2, применяется обычная реализация Sol по утверждённому брифу и независимое
ревью Opus; Opus при этом не автор принимаемого дизайна/материала. V3 требует
своего разрешения и остаётся закрытым без verifier. Уже созданный Opus
кандидат V2/V3 нельзя переименовать в «авторство Sol» ради обхода gate: при
отсутствии независимого маршрута задача блокируется с точной причиной.

Sonnet и Fable исключены из целевого состава. Gemini и старые Sol/Opus не являются активными fallback 3.0. Отказ поставщика не разрешает понижать effort, менять семейство или модель молча. Можно повторить безопасный pre-side-effect запрос либо выбрать другой уже разрешённый маршрут, сохраняя scope и verification floor; после начала неизвестного побочного действия сначала recovery.

Один репозиторный routing source задаёт модели, усилия и floors; skills описывают функции. Launcher передаёт точную модель/effort; evidence различает requested и reported model. Ответ провайдера подтверждает сообщённую идентичность, но не является независимой аттестацией его внутренних маршрутов. `none` не поддерживается Sol 6.1/Astra; Luna `none/low/medium/max` запрещены проектной политикой независимо от общей API-поддержки.

### Пропорциональная проверка

- **V0:** безопасная локальная micro-задача, обратимость, точный oracle, отсутствие существенной неопределённости. Один focused proof и self-review, затем контроллерская приёмка; независимый reviewer не нужен.
- **Содержательный пробел proof:** для реализации `gpt-6.1-sol`/`gpt-6-luna` требуется независимый `claude-opus-5-5`. В первой 3.0 обратный V1-маршрут Sol допускается только для низкорискового результата автора `executor=claude`, `model=claude-opus-5-5`, в отдельном запуске. Любой `executor=codex` либо автор с GPT-ID из целевой матрицы исключён из этого обратного маршрута; несогласованные adapter/model пары отвергаются. `agy/other` не получают разрешение по условию «всё, что не Codex». Сохранить смысл существующих V1/V2 вместо нового слоя классификации; автор не проверяет собственный результат.
- **Medium/high risk:** действующие минимумы и specialist gates обязательны. V3 не обходится, budget exhaustion не уменьшает проверку.
- Блокирующее finding содержит место, условие, нарушенный критерий, последствие и способ проверить. «Можно улучшить» — предложение вне заказа. Нет квоты на находки.
- Ревьюер получает исходный заказ, фактический кандидат, контекст и proof; убедительный самоотчёт автора не заменяет эти входы. После исправления проверяются изменённый кандидат и затронутые условия. Доказательства переиспользуются только при совпадении файлов, команды и релевантного окружения.

Пример V0: заменить точно указанную опечатку в разрешённом README; фактический diff показывает только нужную замену. Non-V0: изменить бизнес-логику по неоднозначному описанию, даже если lint зелёный. Exit code 0 сам по себе не oracle: нужна наблюдаемая связь proof с результатом и проверка отсутствия лишнего изменения. `terminalGate=true` требует `reviewer=none` в самом review-order; контроллер отвергает вложенное назначение. Невалидный результат reviewer разбирается как ограниченная ошибка результата, а не повод для третьего ревизора. Продуктовая коррекция получает новую попытку той же миссии и применимую перепроверку, не обнуляя budget.

## 6. Минимальный технический состав

Существующие Python scripts в `integrations/hermes-legion-kit/skills/autonomous-ai-agents/agent-contract-runner/scripts/` остаются основой. Обозначение `runner/` ниже относится к этому каталогу.

| Ответственность | Существующая поверхность | Изменение |
| --- | --- | --- |
| Mission lifecycle | `agent_contract_runner.py`, `execution_state.py`, `attempt_ledger.py` | Один владелец переходов/лимитов; устойчивое восстановление без второго scheduler |
| Решение model/risk | `review_ladder.py` и связанные routing references | Риск по реальным эффектам; функциональные роли; матрица §5, политика 3.0 |
| Подготовка поручения | `order_preflight.py`, существующая сборка order | Проверить transport/argv/env, входы, пути, capabilities до child launch |
| Приём результата | `agent_result_builder.py`, `response_envelope.py`, `result_gateway.py`, `direct_custody.py` | Служебные поля принадлежат контроллеру; исходный результат сохраняется; malformed content не превращается в успех |
| Scope и артефакты | Существующие guards, `artifact_lineage.py`, фактический snapshot/diff | Учитывать tracked/untracked, delete/rename, symlink/mode/binary; отличать dirty baseline и scratch от новых продуктовых изменений |
| Решение о продолжении | `progress_drift_detector.py`, `blocker_packet_projection.py` | Подсказки одному управляющему циклу; подмножество путей допустимо, расширение цели нет |
| Инструкции и поставка | `skills/`, Claude/Codex/Hermes kits, overrides, существующие installers | Один активный словарь и политика; условные references; отсутствие старого override после cutover |

Проверка фактических записей обязательна. Worktree отделяет изменения, но не ограничивает права процесса; применять доступную реальную границу инструментов/FS и фиксировать её ограничения. Hash/receipt доказывает наблюдаемую целостность, не абсолютное авторство или защиту от процесса с равными правами.

Служебное восстановление допускает только данные, которые контроллер уже знает, вне авторского payload. Нельзя придумывать findings, proof, status, исправлять identity под ожидаемую или переписывать канонический результат автора. Raw JSON/fence/wrapper извлекается детерминированно без модели. Для новых 3.0 orders malformed transport сохраняется как **protocol-failure receipt**, не как synthetic executor `failed` в конечном `resultPath`. Canonical result создаётся ровно один раз после валидного авторского ответа; реальный валидный `failed` автора сохраняется без повышения статуса. Старые finalized results не открываются заново.

Если недостаёт авторского содержания, допускается максимум одна **report attempt того же order**, со свежим controller-owned attempt id и output namespace внутри исходного control root. Это отдельный модельный запуск, но не новый product order и не product replay. Controller предъявляет неизменный order, сохранённые raw/proof/product snapshot и явный режим «только отчёт», технически убирая product-write/side-effect tools; первоначальный `launch.command` не исполняется повторно. Ответ содержит исходный `orderId` и handoff, поэтому проходит прежний V1 validator. Новый raw candidate и reporting start/closure связываются с исходным launch, raw и snapshot; исходные bytes/receipts не меняются. После проверки controller однократно создаёт первоначальный `resultPath` и acceptance, содержащий эту связь. Downstream `inputResults` ссылается на исходные orderId/result/acceptance/closure; acceptance verification дополнительно проверяет reporting receipt/candidate и неизменность snapshot. Если report невалиден, closure/state фиксируют protocol failure без фиктивного результата модели. После одной неудачи — честный blocker/failed, без цикла.

Идемпотентный ключ — `(mission, task, productAttempt, reportOrdinal=1)`; после restart контроллер собирает результат существующей report attempt, не создаёт новую. Модель возвращает текст в канал; candidate/result files пишет CLI/controller. «No-write» запрещает изменения продукта, не сохранение output контроллером. Использовать существующий Codex read-only sandbox с запрещённой сетью/эскалацией либо Claude с пустым набором tools/MCP и проверенной изолированной конфигурацией без hooks/background writers. Permission mode сам по себе не доказательство FS-изоляции; нового guard/sandbox framework не добавлять. Если такой режим не подтверждён, model correction отключена; deterministic recovery и честная protocol failure остаются. Только доказанный продуктовый дефект создаёт fix-order. При неизвестном эффекте сначала recovery процесса; `unknown_effect` — причина в state, не новый mission status. Resume только по записанному session id, без `--last`/`--continue` общей папки.

## 7. Единая последовательность реализации

Каждый этап — проверяемый срез, а не обязательный отдельный агент. Инженер реализует, тимлид принимает; reviewer назначается по §5. Все этапы пока **не начаты**. Никаких общих `git add .`, установки или release-тега при подготовке плана.

### N3. Устранить служебные повторы и обеспечить фактический scope

- Зависимости: N1/N2. Владелец: инженер Sol; reviewer Opus; специалист по доступу только для конкретного пробела изоляции.
- Preflight до запуска: namespace, inputs, output, transport, argv/env, scratch. После запуска: immutable raw result, ограниченная нормализация известных metadata, проверка фактических изменений против dirty baseline и критериев.
- Согласовать существующие Codex/Claude adapters к одному builder: Codex `--output-schema`/`--output-last-message`, Claude `structured_output`/explicit terminal result. Hermes `--format stream-json` остаётся способом наблюдать автоматизированный запуск тимлида, не новым executor adapter. Сохранять полный raw wrapper/stream; выбирать ровно один candidate source; native schema не заменяет strict identity/scope/diff/proof.
- Исправить CT02–CT05: structured-output extraction, Codex schema flag, strict post-adapter validation, и запрет Hermes native delegation correction в product path. Hermes schema validity не является controller acceptance.
- После side effect malformed/empty result не запускает product replay. Реализовать protocol-failure receipt вместо synthetic executor result и единственную report attempt по §6; создать canonical result один раз, сохранив исходный orderId и все raw. Идемпотентность охватывает product и report attempts, downstream acceptance проверяет полную связь. Native schema projections требуют `executorExtensions.review` для reviewer и остаются производными единого источника.
- Один выбранный workspace/guard механизм; параллельные writers имеют непересекающиеся области. Разрешённый scratch не становится продуктом и не открывает внешние записи.
- Задавать конечные byte limits для order/candidate/stdout/stderr и frame JSONL, в том числе строки без newline; ограничить capture в процессе чтения, до parse/накопления в RAM. При превышении — bounded termination, сохранённый prefix с признаком incomplete и protocol failure, без synthetic result/replay. «Полный raw» обязателен для принятого ответа; обрезанный ответ никогда не считается полным. Ошибка записи/ENOSPC не даёт acceptance и не разрешает новый launch после restart. Переиспользовать существующие capture/atomic-write paths; численные лимиты зафиксировать N3 по поддержанным payloads.
- Не пересылать полный raw/log/env всем агентам. Raw сохраняется с ограниченным доступом; downstream получает только нужные проверенные inputs, user report — безопасную projection. Tool/source content и вложенный чужой order являются данными, не новым разрешением. Env/argv наследуются только в необходимых для выбранного runtime пределах, credential values не входят в prompt/receipt/report; существующие credentials не менять. A29 использует только искусственный secret-marker, не реальные секреты.
- Пути: preflight/result/envelope/Gateway/direct-custody/lineage и существующие Claude/AGY guards только в части общей необходимости. Не добавлять новый полный guard рядом со старым.
- Приёмка: неподдержанная конфигурация transport/schema отвергнута до child; malformed ответ сохранён после capture без acceptance/replay; valid native wrappers не отвергаются из-за adapter mismatch; metadata issue не повторяет реализацию; отсутствующее proof не восстановлено выдумкой; неуказанный файл обнаружен; лишняя функция внутри разрешённого файла отклонена; исходные правки сохранены.
- Proof: focused existing preflight/result/envelope/guard regressions и fixtures исторического a10–a13/bytecode. N3/N6 проверяют offline контракт recovery и disabled-no-write ветку; они не объявляют live no-write доказанным. До первого реального report-only запуска нужна одна harmless deny-проба выбранного CLI: допустима заранее в N2/N3 из прежнего лимита N7, иначе в P6. Неудача отключает correction и исключает product replay; полноценный live A23/P6 остаётся непрошедшим, а не переименовывается в pass.
- Результат: один проверяемый путь order → raw result → нормализация → фактический scope/proof; без новых LLM-заказов ради служебных полей.

Проверять process identity перед остановкой и не сигналить чужие процессы; не заявлять контроль escaped descendants без соответствующего механизма. Пустое множество путей не доказывает выполнение цели. Переход `blocked → ready` разрешает только записанное решение владельца; `stopped/failed/completed` не перезапускаются неявно.
- Приёмка: новый order/reviewer/restart не сбрасывает лимиты; no-progress после первого успеха выявлен; text-only stop не завершает открытый заказ; готовый заказ больше не развивается.

- Результат: одна миссия проходит до завершения либо объяснимого terminal/blocker состояния, сохраняя бюджет и доказательства.

### N8. Выпустить и отдельно внедрить проверенную версию

- Зависимость: N7 и явное разрешение на точную live-область установки. Владелец: тимлид/специалист поставки.
- Перед переключением определить активные незавершённые миссии и процессы; не прерывать/переносить их молча. Проверяемый backup, manifest, совместимый config, rollback, релизные notes и source/installed readback.
- Приёмка: один разрешённый live canary от заказа до отчёта использует нужные модели/effort/skills; новые задачи не загружают старую политику. HTTP 200, успешный import или restart не являются такой приёмкой.
- При провале canary остановить новые назначения; восстановить предыдущие bytes/режим проверенным rollback, не теряя evidence и не повторяя неизвестные действия. Тег/публикация только после применимых проверок и разрешения на публикацию.
- Proof/результат: release manifest, readback, canary evidence и выполненная fixture-проверка rollback. Порядок отката: закрыть dispatch → установить состояние процессов → сохранить новое evidence/state отдельно → восстановить только manifest-owned файлы и ранее разрешённые config → проверить модель/политику/skills → разрешить новые задания. State 3.0 не передаётся старому runtime; незавершённая миссия остаётся явно остановленной до отдельного решения, без автоматического replay. Пилот N7 изолирован: его провал не требует отката живой 2.6.

Последовательность: **N1 → N2 → N3 → N4 → N5 → N6 → N7 → N8**. Небольшие синхронные правки инструкций входят в свой срез. Параллелизм возможен только для независимых результатов/непересекающихся записей, а не ради числа ролей.

Каждый A-сценарий относится к существующему regression/eval, не создаёт новую универсальную suite. Невыполненный обязательный сценарий не отмечается pass. Старые S1–S14 покрываются A01–A16, а дополнительные случаи относятся к новой границе версии и реальным маршрутам.

## 10. Фиксация плана и правило завершения работы

Предыдущий запрос завершён фиксацией плана 1.4. Новый запрос пользователя разрешает реализацию по этому единому плану, назначение субагентов под управлением GPT-6.1 Sol и проверку их результата. Рабочая область — отдельная implementation worktree; исходные пользовательские изменения сохранены в прежней worktree. Push, production changes и установка в рабочий Hermes не разрешаются самим фактом реализации.

Ревью получает ограниченный пакет: этот план, утверждённые пользовательские ограничения, реестр проблем и проверенные исходные фрагменты. Claude не правит проект, не запускает других агентов и не использует secrets. Точное содержимое кандидата связывается SHA-256 с результатом; ответ сохраняется отдельно от controller acceptance. Замечания принимаются по доказательствам, а не по авторитету модели.

Уточнение владельца от 2026-10-18: большие задания Claude заранее делятся на
небольшие подзадачи по одному проверяемому вопросу. Каждая получает релевантный
diff, необходимые определения и места вызова, критерий проверки и один короткий
результат; весь проект и история переписки повторно не передаются. Для source
review сохраняются commit, диапазоны исходников и SHA-256 каждого входа.
Связь между срезами проверяется отдельным узким заданием, когда она существенна;
итоги объединяет тимлид, без повторного монолитного review-of-review. Недостаток
контекста фиксируется как INCOMPLETE с точным запросом недостающего фрагмента,
а не как ACCEPT. Таймаут не вызывает автоматического повтора: сохраняются
исходный receipt и расход запуска; меняется конкретная граница задания либо
исследуется провайдер в оставшемся бюджете. Декомпозиция не снижает требуемый
уровень рассуждения и не продлевает утверждённый заказчиком общий лимит. В
текущем продолжении P6 назначены четыре source-review среза; после timeout
один из них разделён ещё на два вопроса. Два дополнительных запуска учтены
отдельно, общий предел этого продолжения — шесть. Исторические пилотные миссии
не повторяются. Фактические результаты и оставшаяся декомпозиция — в отчёте r4.

После разбора замечаний статус плана обновляется; решения и остаточные ограничения фиксируются в отдельном отчёте ревью. Реализация принимается только после соответствующих N-stage checks; никакой документ или положительный вердикт Claude не объявляет CENTURION 3.0 готовой системой.

## 11. Исполняемый план создания версии 3.0

Этот раздел превращает N1–N8 в один управляемый граф работ. Он не создаёт
второй план, новый controller или дополнительные модели. Тимлид владеет
границами, интеграцией и финальным решением; субагенты под управлением
`gpt-6.1-sol` изменяют только назначенные им непересекающиеся поверхности.

### 11.1. Общий порядок

1. **Freeze и baseline.** Тимлид фиксирует commit, dirty baseline, разрешённые
   пути и текущие regression commands. Пользовательские изменения не становятся
   частью 3.0 автоматически.
2. **N1 contract gate.** Фиксируются policy/state/tunnel contracts, единственный
   Gateway launcher, routing source и границы старых orders. Без этого gate
   остальные изменения не принимаются.
3. **N2 routing gate.** Обновляются model/effort/risk floors и routing fixtures.
   Luna работает только на `high|xhigh`; Sol является основным тимлидом и
   исполнителем сложных задач; Astra остаётся read-only advisory; Opus —
   независимый reviewer и специалист по дизайну.
4. **N3/N4 execution gate.** Собираются preflight, adapters, bounded capture,
   create-only result/recovery и один controller loop. Product effect и report
   attempt имеют разные idempotency keys; malformed report не повторяет продукт.
5. **N5 skills gate.** В активный core попадает только короткий контракт;
   domain skills/tools загружаются условно. Legacy/maintenance surface не
   получает dispatch authority. Проверяется loaded chain bundle → skills →
   project/global instructions → hooks/MCP.
6. **N6 isolated release candidate.** Сборка и install fixture выполняются в
   изолированных homes/config. Проверяются source/installed hashes, capabilities,
   rollback и отсутствие v2 fallback. Рабочий Hermes не изменяется.
7. **N7 pilot gate.** В изолированной сборке выполняются offline A01–A30 и
   ограниченный P1–P6 с общими лимитами плана. Отсутствующее capability или
   неполный сценарий остаются `not_run`/failed и блокируют принятие.
8. **N8 release decision.** Тимлид проверяет полный diff, результаты, риски и
   готовность rollback. Установка в рабочую среду не выполняется без отдельного
   разрешения на конкретный manifest и canary.

### 11.2. Пакеты субагентов

| Пакет | Исполнитель | Зависимость | Разрешённая поверхность | Обязательный результат |
| --- | --- | --- | --- | --- |
| W1 · routing/contract | Sol-1 | Freeze; N1→N2 | `review_ladder.py`, routing references, `mission-prep.mjs`, routing regressions | Один routing source; корректные model/effort/reviewer floors; все восемь routing cases проходят |
| W2 · tunnel/admission | Инженер Sol под управлением Sol-тимлида | N1; согласованные W1/W3 interfaces | `order_preflight.py`, `response_envelope.py`, `agent_result_builder.py`, `result_gateway.py`, `accepted_inputs.py`, связанные regressions | Strict ingress, bounded capture, review binding, no replay и protocol-failure receipts |
| W3 · lifecycle/recovery | Sol-тимлид, владелец интеграции | N1; приёмка после W2 | `agent_contract_runner.py`, `execution_state.py`, `attempt_ledger.py`, `progress_drift_detector.py`, `blocker_packet_projection.py`, lifecycle regressions | Один writer/lock, Gateway-only launch, budget/deadline/cancel, compaction reload, unknown-effect recovery, no-progress и idempotent restart |
| W4 · skills/release | Sol-4 | W1–W3 contracts | active skills/manifests, Hermes/Codex/Claude kit surfaces, installer/smoke fixtures, related docs/tests | Progressive loading map, legacy exclusion, loaded-chain readback, isolated install/rollback fixture |

Sol-тимлид работает в отдельной integration worktree; пакеты получают отдельные
worktree-ветки либо непересекающиеся файлы этой worktree по записанному назначению.
Одновременно у тимлида не более двух исполнителей; после завершения пакета
агента можно назначить на следующий. Изменения W2/W3 разрабатываются после
согласования интерфейсов, но принимаются в порядке N3 → N4. Агент не
трогает чужие файлы, рабочий Hermes, глобальные settings, credentials, install
targets или production. Если изменение требует пересечения поверхностей, агент
останавливается с вопросом к тимлиду и не редактирует чужой файл. Каждый агент
возвращает список файлов, команды proof, фактический diff, ограничения и
остаточные риски; утверждение текста агента не заменяет проверку контроллера.

### 11.3. Интеграция и проверки

- После W1 тимлид запускает routing regressions и проверяет, что dirty baseline
  сохранён. При провале W2–W4 не стартуют.
- После W2/W3 тимлид запускает полный offline runner set, затем проверяет
  межпакетные contract fixtures A07–A10, A21–A30. Никакие legacy green tests
  не переименовываются в pass 3.0.
- После W4 тимлид проверяет loaded-chain manifest, source/installed readback и
  isolated smoke. Внешние provider calls и live correction разрешаются только
  внутри N7 budget и capability receipts.
- Тимлид проводит итоговый review staged diff: scope, ownership, security,
  tests, no-op/stub search, failure paths, process termination и сохранность
  девяти исходных runtime-файлов в исходной worktree. Их копии в implementation
  worktree адаптируются только по явному решению N1. Reviewer не назначает сам себя и не запускает
  дополнительные циклы review-of-review.
- Версия считается готовой только если N1–N7 имеют evidence и все обязательные
  gates пройдены. Иначе итоговый статус `blocked`/`failed` с конкретным
  boundary; N8 и live install не считаются выполненными.

### 11.4. Решение N1 для реализации

Владеющий entrypoint исполнения — существующий `result_gateway.py`;
`agent_contract_runner.py` остаётся общим ядром validation/proof/state.
Прямой `--mode run` runner не запускает policy 3.0. Один изменяемый mission
state расширяет существующий Loop state; `execution_state.py` остаётся
read-only projection. Ledger и capture receipts — evidence, не второй
источник полномочий. Счётчики и dispatch intent записываются под одним lock
до spawn, незавершённый intent после restart не разрешает новый запуск.

W2 отвечает за native adapters, bounded capture и protocol-failure receipts.
W3 отвечает за policy/mission binding, состояние/лимиты и привязку этих
механизмов к Gateway после приёмки W2. Межпакетная правка Gateway проводится
только после завершения его владельца W2. Report correction остаётся выключенной
до доказательства no-write; отсутствие capability не разрешает product replay.

Девять сохранённых исходных файлов разбираются так:

- `order_preflight.py` и его regression — адаптировать в W2 после чтения
  исходной незакоммиченной версии, проверить актуальные argv/native schema.
- `progress_drift_detector.py`, `blocker_packet_projection.py` и их regressions —
  адаптировать в W3: path inclusion, no-progress и internal/external decision.
- Прежний diff `agent_contract_runner.py` — перенести только необходимую
  интеграцию preflight после согласования интерфейса; остальное выполнить по 3.0.
- `autonomy-authority.schema.json` и `autonomy-trust-contract-design.md` —
  design-only, оставить вне новой поставки; исходные bytes сохранить.

Эти решения не принимают старые реализации заранее. Проверяется фактическая
версия в новой ветке; исходная worktree остаётся неизменной. Контроллер сохраняет
канонические authority/acceptance decisions, специалисты не расширяют заказ.
