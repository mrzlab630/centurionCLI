Дата: 2026-10-16. Целевая основная версия: **3.0**; текущая основная версия в README: 2.6. Ветка: `feat/centurioncli/v3-autonomous-team`; исходный HEAD: `ab1c851749baf4d6deb354c12c2f609498ca678a`.

Версия плана: **1.0**. Реализация не начата. Статус независимой проверки и фиксации: [отчёт ревью](CENTURION_3_0_PLAN_REVIEW.md). После фиксации он становится единственным планом реализации 3.0; прежние документы остаются исследовательскими материалами, а не параллельными инструкциями.

## 1. Результат версии и границы работы

Заказчик утверждает цель, ограничения, критерии готовности, бюджет и полномочия. Один тимлид принимает заказ и самостоятельно доводит его до готового результата: строит план, назначает исполнителей, решает технические вопросы, проверяет работу и возвращает итоговый отчёт. Промежуточные сообщения сообщают о ходе работы; обычные технические решения не требуют ответа заказчика.

Главные критерии 3.0: завершённый утверждённый заказ; отсутствие незапрошенных функций; отсутствие обычных промежуточных согласований; проверяемое качество; конечный процесс без циклов улучшений и review-of-review. Невозможность завершения сообщается честно с конкретным внешним блокером или исчерпанным лимитом.

В реализацию входят управляющий цикл, полномочия, назначение моделей, применимые проверки, согласованные активные skills и поставка новой версии. Не входят новая БД, очередь, сервис классификации, dashboard, общая платформа доверия, полное переписывание всех инструментов, дополнительные модели, очистка старых результатов, автоматический exploit, production deploy или изменение пользовательских credentials. Установка в рабочий Hermes — отдельный финальный этап с конкретной областью и разрешением.

## 3. Граница 3.0: что сохраняем и что прекращаем

**Новая версия — единый новый процесс на проверенных существующих механизмах.** Меняем управляющие решения в текущем runner на отдельной ветке; не строим второй конкурирующий runner и не поддерживаем две политики для новых заказов.

| Область | Решение для 3.0 |
| --- | --- |
| Активные роли | Функциональные имена: тимлид, инженер, архитектор, дизайнер, reviewer, применимый специалист. CENTURION — бренд; римские aliases допустимы в отображении, но не задают полномочий |
| Состояние заказа | Один controller-owned mission state; существующие order/result, ledger и execution events используются по назначению. Не создавать вторую изменяемую копию одного состояния |
| Старые orders/results | Не переписывать, не принимать заново, не переводить автоматически в 3.0. Новый runtime отклоняет попытку продолжить старый заказ как новый; незавершённый заказ сначала явно завершается/останавливается в прежнем режиме либо получает новый согласованный заказ с явным переносом результатов |
| Формат обмена | Сохранить проверенный V1 wire format там, где он достаточен. Явная `policyVersion: "3.0"` в controller-owned context обязательна для новых миссий и связывается с mission state; значение из текста исполнителя не авторизует новую политику. Отсутствие/неизвестная версия не включает скрытый legacy fallback |
| Совместимость | Старые артефакты доступны для чтения. Старые модели, команды, aliases и специальные пути не становятся обязательной поддержкой активного 3.0. Сохранение общего wire parser не означает сохранение старых разрешений |
| Обязательные церемонии | Убрать глобальные WAR ROOM, tribunal, review-of-review, согласование каждого файла и ровно две попытки на любой заказ |
| Полезные механизмы | Сохранить проверку identity/artifact, preflight, фактического diff, необходимых proof, create-only исходных результатов и независимости автора/reviewer |
| Установки и откат | До отдельного внедрения активная 2.6 не меняется. Откат восстанавливает проверенный набор файлов/config и не возобновляет неизвестные процессы или неподтверждённые побочные эффекты |

В рабочей копии сохранены девять исходных изменений runner/preflight/detector/blocker/schema. Их не считать принятыми автоматически. В N1 каждому назначается решение: переиспользовать после focused proof, адаптировать либо оставить вне поставки. Design-only trust schema не входит в минимальную 3.0. Ничего из этих исходных файлов не удаляется при фиксации плана.

Версии различаются: **product 3.0.0** обозначает релиз, **policyVersion 3.0** — применяемые полномочия и routing, **stateVersion** — форму сохраняемого controller state, **kit version** — совместимость устанавливаемого пакета. Существующие order/result V1 не обязаны менять номер. Несовместимое обязательное поле, новый формат state или изменение authority/acceptance требуют явного перехода; багфикс не даёт старому order новых прав. Старый runtime может не понимать новый metadata: поэтому 3.0 dispatcher проверяет объявленную capability runtime до передачи заказа, а не надеется, что старый бинарник сам его отвергнет. Upgrade/rollback fixture проверяет эту границу.

## 4. Полномочия и единый рабочий цикл

```text
Заказчик: цель, критерии, бюджет, доступ и внешние действия
    ↓
Тимлид: план → поручение → результат → проверка → приёмка → итоговый отчёт
    ├─ исполнитель с необходимыми skills
    ├─ отдельный аналитик/дизайнер по конкретной необходимости
    └─ независимый reviewer по риску и пробелу доказательств

Программный controller обеспечивает состояние, границы, запуск и учёт доказательств.
```

Тимлид может менять декомпозицию, порядок, модель в разрешённой матрице, технический способ и необходимые локальные файлы/тесты внутри утверждённой области. Исполнитель не расширяет своё поручение и не делегирует дальше без назначения. Reviewer сообщает findings тимлиду, не правит продукт, не ослабляет критерии и не назначает другого reviewer.

Заказчик нужен только для существенно неразрешимой неопределённости цели, расширения полномочий/бюджета либо требуемого внешнего решения. Новая функция продукта, платёж, production deploy, секрет, изменение аутентификации, необратимая операция или публикация не становятся разрешёнными из-за общего слова «автономно». Если соответствующее действие уже явно согласовано и технически поддержано, повторный вопрос ради той же авторизации не нужен. Действующий V3 остаётся закрытым без необходимого проверяемого разрешения; создание такого verifier не является предпосылкой обычной локальной разработки 3.0.

При приёме заказа тимлид записывает ссылку на конкретное решение заказчика и его границы: цель/non-goals, продуктовые критерии, разрешённые среды/пути, классы действий и лимиты. Контроллер связывает этот снимок с mission ID/policy и проверяет перед dispatch. Текст исполнителя «заказчик разрешил» или наличие одного `policyVersion` не являются разрешением. Если для чувствительного действия нужен trusted verifier, обычная ссылка на разговор его не заменяет.

Примеры: новый файл контроллера и focused test для заказанного endpoint — техническая декомпозиция; новый endpoint, несовместимый API-контракт или новая платная зависимость — изменение заказа/полномочий. Тимлид выбирает локальный способ в принятом стеке; замена согласованного языка/платформы не разрешается по умолчанию. Новый helper допустим только при технической необходимости для исходного результата, а не по общей привычке skill.

Дефект и неполное исполнение одинаково требуют коррекции, если нарушен утверждённый критерий или необходимый инвариант заказанного поведения. Edge case не обязан быть перечислен буквально: например, обработка разрешённых входов — часть корректности endpoint. Новый сценарий продукта сверх цели остаётся предложением. Классификацию делает тимлид по доказательствам; нельзя требовать новых функций под видом качества или отвергать реальный дефект только из-за отсутствия его буквального названия в брифе.

### Состояние и завершение

Состояния миссии: `ready → running → verifying → completed`; коррекция возвращает в `running`, ожидание необходимого внешнего решения — `blocked`, исчерпание лимита/невосстановимый отказ — `failed`. Успех одного поручения не завершает миссию. Переход в `completed` требует закрытых критериев, действительных proof, обязательного ревью и отсутствия незавершённого процесса с неизвестным эффектом.

Существующий `execution_state.py` — **read-only projection из order/result/receipts**, а не хранилище событий или владелец миссии. Изменяемое состояние принадлежит controller в `agent_contract_runner.py`; переиспользуются `loopContract.statePath`, `LoopStateLock` и `atomic_write_loop_state`. В N1 выбранный файл состояния расширяется необходимыми mission metadata, а projection остаётся производной. Минимально требуются: mission ID, policy/state version, ссылка на утверждение, цель/non-goals, критерии, разрешённые действия/пути, лимиты, задания и зависимости, attempts, evidence, acceptance. Детальная JSON-форма фиксируется N1 внутри этого единственного источника; новая БД и дублирующая изменяемая mission state запрещены. Ledger — журнал наблюдений, не второй центр выдачи полномочий.

Перед побочным действием записываются intent и идентификатор попытки; после — наблюдаемый результат. При восстановлении сначала выясняется состояние уже запущенного процесса. Неизвестный внешний эффект не повторяется автоматически. Новый order ID, смена модели, reviewer или restart не сбрасывают mission budget.

Плановая политика локального пилота: общий лимит 45 минут, до 8 модельных запусков на миссию, включая консультации/ревью/повторы; до 3 продуктовых попыток на один ограниченный task. Любой запрос, способный вызвать inference, учитывается до dispatch, включая неуспешный запрос; retry/restart с новым inference не бесплатен. Проверка статуса уже запущенного процесса не считается новым inference, но время продолжает учитываться. После двух последовательных одинаковых блокеров без новых доказательств прежняя стратегия прекращается. Тимлид может один раз сменить подход в остатке лимита; повышение лимита только через прежнюю authority boundary. Эти значения — стартовая проверяемая настройка пилота, не обещание достаточности для любого проекта; реальный заказ фиксирует лимиты при приёме. При неизвестной денежной стоимости действует лимит времени/запусков, cost=`unmeasured`; фиктивный денежный cap не заявляется.

Прогресс — закрытый критерий, новый проверенный результат либо устранённый конкретный дефект. Новый отчёт/hash/роль сам по себе не прогресс. Повтор допускается с конкретной причиной и ожидаемым новым свидетельством.

## 5. Модели, роли и проверка

| Работа | Исходный маршрут 3.0 | Ограничения |
| --- | --- | --- |
| Тимлид | GPT-6.1 Sol `high`, `xhigh` для трудных решений | Один владелец заказа; не подменяет независимую проверку собственного результата |
| Узкая механическая работа | GPT-6 Luna `high`; `xhigh` при оправданной необходимости | Только `high/xhigh`; default `high`; ясный oracle и низкая неоднозначность. Повышение сложности переводит к Sol, не только увеличивает effort |
| Обычная реализация | Sol `medium/high`; сложная — `high/xhigh` | `low` допускается только для механического случая, не как скрытая замена Luna или снижение review floor |
| Сложная архитектура, анализ, диагностика | Astra `high` напрямую по задаче; `xhigh` для сложных/рискованных выводов | Отдельное read-only заключение; не обязательный этап и не терминальный reviewer. В первой 3.0 не расширять усилия до `medium`: прежний план предлагал его без локального proof |
| Визуальный дизайн | Opus 5.5 `high` | Для первой 3.0 — ограниченный низкорисковый дизайн по фиксированному брифу, с допустимой V1-проверкой Sol. Если фактический риск/неопределённость требует V2/V3, маршрут Opus не объявляется доступным без независимого gate; нельзя понижать классификацию ради запуска |
| Независимое ревью реализации Sol/Luna | Opus 5.5 `high`; выше — по конкретному риску | Отдельная сессия и исходные доказательства; неизменный результат не отправлять на повторное полное ревью |
| Проверка низкорискового материала Opus | Sol `high/xhigh`, если применимая политика разрешает | Не открывать обход medium/high-risk gate. Реализация Opus с обязательным V2/V3 остаётся вне первой 3.0 до отдельного доказанного независимого маршрута |

Sonnet и Fable исключены из целевого состава. Gemini и старые Sol/Opus не являются активными fallback 3.0. Отказ поставщика не разрешает понижать effort, менять семейство или модель молча. Можно повторить безопасный pre-side-effect запрос либо выбрать другой уже разрешённый маршрут, сохраняя scope и verification floor; после начала неизвестного побочного действия сначала recovery.

Один репозиторный routing source задаёт модели, усилия и floors; skills описывают функции. Launcher передаёт точную модель/effort; evidence различает requested и reported model. Ответ провайдера подтверждает сообщённую идентичность, но не является независимой аттестацией его внутренних маршрутов. `none` не поддерживается Sol 6.1/Astra; Luna `none/low/medium/max` запрещены проектной политикой независимо от общей API-поддержки.

### Пропорциональная проверка

- **V0:** безопасная локальная micro-задача, обратимость, точный oracle, отсутствие существенной неопределённости. Один focused proof и self-review, затем контроллерская приёмка; независимый reviewer не нужен.
- **Содержательный пробел proof:** для реализации Sol/Luna требуется независимый Opus. Для допустимого низкорискового не-Codex результата возможен Sol. Сохранить смысл существующих V1/V2 вместо нового слоя классификации.
- **Medium/high risk:** действующие минимумы и specialist gates обязательны. V3 не обходится, budget exhaustion не уменьшает проверку.
- Блокирующее finding содержит место, условие, нарушенный критерий, последствие и способ проверить. «Можно улучшить» — предложение вне заказа. Нет квоты на находки.
- Ревьюер получает исходный заказ, фактический кандидат, контекст и proof; убедительный самоотчёт автора не заменяет эти входы. После исправления проверяются изменённый кандидат и затронутые условия. Доказательства переиспользуются только при совпадении файлов, команды и релевантного окружения.

Пример V0: заменить точно указанную опечатку в разрешённом README; фактический diff показывает только нужную замену. Non-V0: изменить бизнес-логику по неоднозначному описанию, даже если lint зелёный. Exit code 0 сам по себе не oracle: нужна наблюдаемая связь proof с результатом и проверка отсутствия лишнего изменения. `terminalGate=true` требует `reviewer=none` в самом review-order; контроллер отвергает вложенное назначение. Невалидный результат reviewer разбирается как ограниченная ошибка результата, а не повод для третьего ревизора. Продуктовая коррекция получает новую попытку той же миссии и применимую перепроверку, не обнуляя budget.

| --- | --- | --- |
| Mission lifecycle | `agent_contract_runner.py`, `execution_state.py`, `attempt_ledger.py` | Один владелец переходов/лимитов; устойчивое восстановление без второго scheduler |
| Решение model/risk | `review_ladder.py` и связанные routing references | Риск по реальным эффектам; функциональные роли; матрица §5, политика 3.0 |
| Подготовка поручения | `order_preflight.py`, существующая сборка order | Проверить transport/argv/env, входы, пути, capabilities до child launch |
| Приём результата | `agent_result_builder.py`, `response_envelope.py`, `result_gateway.py`, `direct_custody.py` | Служебные поля принадлежат контроллеру; исходный результат сохраняется; malformed content не превращается в успех |
| Scope и артефакты | Существующие guards, `artifact_lineage.py`, фактический snapshot/diff | Учитывать tracked/untracked, delete/rename, symlink/mode/binary; отличать dirty baseline и scratch от новых продуктовых изменений |
| Решение о продолжении | `progress_drift_detector.py`, `blocker_packet_projection.py` | Подсказки одному управляющему циклу; подмножество путей допустимо, расширение цели нет |
| Инструкции и поставка | `skills/`, Claude/Codex/Hermes kits, overrides, существующие installers | Один активный словарь и политика; условные references; отсутствие старого override после cutover |

Проверка фактических записей обязательна. Worktree отделяет изменения, но не ограничивает права процесса; применять доступную реальную границу инструментов/FS и фиксировать её ограничения. Hash/receipt доказывает наблюдаемую целостность, не абсолютное авторство или защиту от процесса с равными правами.

Служебное восстановление допускает только данные, которые контроллер уже знает. Нельзя придумывать findings, proof, status или переписывать канонический результат автора. При недостающем содержании — одно ограниченное дополнение в бюджете; повтор той же ошибки переводится в локальный дефект адаптера. Это не новая продуктовая попытка и не повтор опасного действия.

## 7. Единая последовательность реализации

Каждый этап — проверяемый срез, а не обязательный отдельный агент. Инженер реализует, тимлид принимает; reviewer назначается по §5. Все этапы пока **не начаты**. Никаких общих `git add .`, установки или release-тега при подготовке плана.

### N1. Утвердить технический контракт 3.0 и границу перехода

- Зависимости: зафиксированный план. Владелец: тимлид; Astra только при конкретной архитектурной неопределённости.
- Зафиксировать authority §4, канонические функциональные роли, структуру одного mission state, policy version и читаемую карту исключений. Определить один владеющий entrypoint для новых миссий, один источник routing и актуальную цепочку загружаемых инструкций.
- Разобрать девять исходных файлов; выбрать полезные существующие механизмы без переноса старых правил. Не объявлять design-only схемы обязательной зависимостью.
- Пути: существующие contract/routing docs, runner state/context, skills orchestrator/planner и Hermes authority sections. Не менять глобальные домашние настройки.
- Приёмка: таблица «решает заказчик / решает тимлид / исполняет агент» без конфликтов; схема state имеет одного writer; old/missing policy не получает authority 3.0. Согласованный технический файл/тест не требует нового Boss approval.
- Proof: focused contract fixtures и сверка инструкций. Результат N1 не требует полной реализации runner.
- Результат: один согласованный контракт в существующих project docs и карта конкретного state/authority entrypoint; не новый обязательный N1-файл сверх этого плана без технической необходимости.

### N2. Исправить назначения, риск и реальные модельные маршруты

- Зависимость: N1. Владелец: инженер Sol; независимая проверка Opus.
- В `review_ladder.py` отделить фактические эффекты от объяснения. Внести матрицу §5, Luna floor, Astra high/xhigh, запреты недопустимых review-пар и version checks. Не доверять самоклассификации исполнителя.
- Для новых 3.0 advisory-orders Astra заменить текущий обязательный минимум `xhigh` на `high`, сохранив `xhigh` по сложности и применимые downstream V2/V3 floors. Старые orders не мигрируются. `medium` в первой 3.0 не включается. Назначение напрямую означает выбор по задаче, а не право Astra изменять продукт или принимать результат.
- `mission-prep.mjs` оставить необязательной рекомендацией skills; исправить восемь случаев, намерение/отрицания/границы слов/БД. Он не выдаёт разрешений и не определяет safety floor.
- Пути: routing/preflight/dispatch, `skills/orchestrator/scripts/mission-prep.mjs`, существующие routing evals и модельные references. Никаких новых моделей или отдельного LLM-классификатора.
- Приёмка: безопасное отрицание не создаёт V3; реально опасное действие не скрывается объяснением; неподдержанная модель/effort отвергается до launch. Astra доступна по сложной задаче без обязательной неудачи Sol; V2/V3 floors сохранены.
- Proof: `regression_review_ladder.py`, существующий `legion-skill-eval.mjs` с найденными случаями, точные launcher assertions. Реальные provider/tool вызовы выполняются в N7.
- Результат: один routing source и работающий preflight, покрытый найденными отрицательными случаями. Перед основной реализацией зависимого adapter допустим ранний capability-probe из общего лимита N7; отсутствие маршрута блокирует только зависимую интеграцию, не документацию/offline работу.

### N3. Устранить служебные повторы и обеспечить фактический scope

- Зависимости: N1/N2. Владелец: инженер Sol; reviewer Opus; специалист по доступу только для конкретного пробела изоляции.
- Preflight до запуска: namespace, inputs, output, transport, argv/env, scratch. После запуска: immutable raw result, ограниченная нормализация известных metadata, проверка фактических изменений против dirty baseline и критериев.
- Один выбранный workspace/guard механизм; параллельные writers имеют непересекающиеся области. Разрешённый scratch не становится продуктом и не открывает внешние записи.
- Пути: preflight/result/envelope/Gateway/direct-custody/lineage и существующие Claude/AGY guards только в части общей необходимости. Не добавлять новый полный guard рядом со старым.
- Приёмка: malformed transport отклонён до child; metadata issue не повторяет реализацию; отсутствующее proof не восстановлено выдумкой; неуказанный файл обнаружен; лишняя функция внутри разрешённого файла отклонена; исходные правки сохранены.
- Proof: focused existing preflight/result/envelope/guard regressions и fixtures исторического a10–a13/bytecode. Реальное ограничение записи проверяется в N7.
- Результат: один проверяемый путь order → raw result → нормализация → фактический scope/proof; без новых LLM-заказов ради служебных полей.

### N4. Собрать один конечный управляющий цикл

- Зависимость: N3. Владелец: инженер Sol; reviewer Opus.
- Связать mission state, ledger, detector и blocker projection. Реализовать §4: общий бюджет, no-progress, коррекции, ожидание процесса, recovery, финальное завершение. `requiresOwnerDecision` направлять тому, чьё решение действительно нужно.
- Переходы записываются атомарно; повторный controller launch не создаёт второго writer и не запускает повторно неизвестное действие. Никакой дополнительной модели для полей JSON/счётчиков/команды «продолжай».
- Пути: runner/state/ledger/detector/blocker и существующий delegation monitor только при необходимом событии.
- Явно заменить сравнение равенства путей в detector на включение. Пустое/суженное множество не доказывает выполнения цели: критерии проверяются независимо, а исчезновение необходимого результата блокирует приёмку. Переход `blocked → ready` разрешает только записанное решение надлежащего владельца; `failed/completed` не перезапускаются неявно.
- Приёмка: новый order/reviewer/restart не сбрасывает лимиты; no-progress после первого успеха выявлен; text-only stop не завершает открытый заказ; готовый заказ больше не развивается.
- Proof: existing runner/state/detector/blocker regressions с interleavings, restart, одинаковым блокером и исчерпанием лимитов. Не расширять в общий distributed scheduler.
- Результат: одна миссия проходит до завершения либо объяснимого terminal/blocker состояния, сохраняя бюджет и доказательства.

### N5. Согласовать ревью и активные skills с новой архитектурой

- Зависимости: N2–N4; конфликтующее правило править синхронно с соответствующим этапом, не ждать N5.
- Владелец: тимлид/редактор; Opus проверяет конкретные authority-противоречия.
- Короткие entrypoints: назначение, результат, границы, применимые действия. Общие recipes в references. Один исполнитель использует несколько skills; отдельные agents только по назначению.
- Убрать перечисленные R13–R20 противоречия: reviewer fixes, любой failed test → fix, обязательные WAR ROOM/tribunal, coverage 80%, test/commit/revert каждой правки, автоматические helper/publish, стиль поверх брифа. Исправить обещание Ferrata/SICARIUS и неописанного Legatus описанием фактического workflow.
- Пути: активные orchestrator/coder/reviewer/tester/refactorer/praemonitor/censor/prompt-engineer/aedilis/pictor/pontifex/error-handler/tabularius entrypoints, `CLAUDE.md`, kit templates/overrides. Все 38 entrypoints проверить на конфликт с authority; доменные references не переписывать массово без найденной проблемы.
- Приёмка: один функциональный словарь; нет двух активных копий skills; модельная политика не дублируется в биографиях; optional improvement не порождает работу. Терминальный reviewer не правит продукт и не назначает следующего reviewer.
- Proof: focused instruction search, skill surface/drift/eval, `regression_legion_handoffs.py`, acceptance fixtures. Размер библиотеки не подменяет измерение реально загружаемого контекста.
- Результат: согласованный активный каталог и короткие управляющие инструкции; R13–R20 не остаются обязательными правилами в поставке.

### N6. Подготовить единую поставку 3.0 в изолированной среде

- Зависимости: N3–N5. Владелец: инженер/специалист поставки; Opus проверяет итоговый срез.
- Direct/Gateway используют одно проверяющее ядро; старые завершённые артефакты доступны только как история. В installer fixture собрать полный активный комплект без старого conflicting override и без v2 fallback для новых миссий.
- Version metadata: основное имя 3.0.0/rc до релиза; версии отдельных kits менять по фактическим breaking changes, сохраняя один manifest совместимости. Номер продукта не диктует новую JSON schema без необходимости.
- Пути: существующие installers/smoke/package metadata, README/docs; exact install manifest фиксируется перед N8. Не трогать live homes на этом этапе.
- Приёмка: cold install и upgrade fixture выбирают только политику 3.0; старые миссии не продолжаются автоматически; новый результат проходит полный цикл, включая одну коррекцию, formatting recovery и restart.
- Proof: relevant existing integration regressions, `node integrations/hermes-legion-kit/scripts/smoke.mjs`, kit smoke по затронутым адаптерам. Один сводный прогон после focused proof; обязательные checks репозитория сохраняются.
- Результат: воспроизводимый release candidate, install manifest и проверенный fixture rollback; рабочий Hermes ещё не изменён.

### N7. Доказать поведение на ограниченном модельном пилоте

- Зависимость: N6. Владелец: тимлид; инженер собирает evidence, независимая проверка по §5.
- Использовать существующий `aquila-executor-eval`; никаких новых benchmark/dashboard. Сначала весь набор §8 offline, затем шесть реальных миссий: micro; bugfix с новым файлом/тестом; UI по брифу; сложный анализ Astra; исправление после reviewer; работа с восстановлением/блокером.
- До пилота проверить реальный supported route каждого выбранного провайдера, model/effort и tool round-trip. Для Sol/Luna применять Responses. Фактическое ограничение записи доказать harmless deny-case в выбранной среде. Не менять глобальный sandbox для имитации успеха.
- Начальный предел пилота: до 8 capability/tool проб плюс шесть миссий по §4 (до 48 запусков); **общий максимум 56 inference-запусков и 5 часов wall time**, включая ранние пробы N2 и любые повторы. Внутри миссии остаются 8 запусков/45 минут; никаких дополнительных recovery-запусков вне лимита. При обходе authority или потере контроля — ранняя остановка. Неполный набор честно отмечается, не считается принятым пилотом.
- Приёмка: все критерии выбранных миссий выполнены, нет незапрошенных функций/обычных вопросов/пропущенных заложенных дефектов/неизвестных повторённых эффектов. Зафиксированы реальные остановки, latency и число повторов; цена у поставщика только если известна.
- Для сравнения накладных расходов использовать доступные существующие baseline задачи; не запускать всю v2 заново и не объявлять процент экономии без сопоставимого baseline. Пилот проверяет пригодность, не статистическое лидерство моделей.
- Proof/результат: один отчёт существующего eval с шестью строками миссий, exact inputs/model/effort, артефактами, решениями и счётчиками; отказ, timeout или непроведённый случай остаётся непрошедшим.

| Миссия пилота | Фиксированный результат и проверка | Сценарии |
| --- | --- | --- |
| P1: опечатка | Одна заданная замена в README, никакого другого diff, Luna high/V0 | A01/A04/A16 |
| P2: bugfix | Заданная ошибка локального endpoint; исправлен конкретный вход, необходимый новый файл/focused test, исходная чужая правка сохранена | A02/A04/A06 |
| P3: UI | Форма по утверждённому брифу и референсу; проверены оговорённые состояния и viewport, нет нового OAuth/анимации/дизайн-фичи от reviewer | A03/A11/A12 |

Точные fixture bytes/брифы фиксируются перед первым запуском и не меняются ради зелёного результата. Таблица задаёт минимальный сценарий, а не разрешение строить шесть полноценных проектов. Полный A01–A16 остаётся offline proof; шесть live миссий не заменяют все комбинации recovery.

### N8. Выпустить и отдельно внедрить проверенную версию

- Зависимость: N7 и явное разрешение на точную live-область установки. Владелец: тимлид/специалист поставки.
- Перед переключением определить активные незавершённые миссии и процессы; не прерывать/переносить их молча. Проверяемый backup, manifest, совместимый config, rollback, релизные notes и source/installed readback.
- Приёмка: один разрешённый live canary от заказа до отчёта использует нужные модели/effort/skills; новые задачи не загружают старую политику. HTTP 200, успешный import или restart не являются такой приёмкой.
- При провале canary остановить новые назначения; восстановить предыдущие bytes/режим проверенным rollback, не теряя evidence и не повторяя неизвестные действия. Тег/публикация только после применимых проверок и разрешения на публикацию.
- Proof/результат: release manifest, readback, canary evidence и выполненная fixture-проверка rollback. Порядок отката: закрыть dispatch → установить состояние процессов → сохранить новое evidence/state отдельно → восстановить только manifest-owned файлы и ранее разрешённые config → проверить модель/политику/skills → разрешить новые задания. State 3.0 не передаётся старому runtime; незавершённая миссия остаётся явно остановленной до отдельного решения, без автоматического replay. Пилот N7 изолирован: его провал не требует отката живой 2.6.

Последовательность: **N1 → N2 → N3 → N4 → N5 → N6 → N7 → N8**. Небольшие синхронные правки инструкций входят в свой срез. Параллелизм возможен только для независимых результатов/непересекающихся записей, а не ради числа ролей.

Каждый A-сценарий относится к существующему regression/eval, не создаёт новую универсальную suite. Невыполненный обязательный сценарий не отмечается pass. Старые S1–S14 покрываются A01–A16, а дополнительные случаи относятся к новой границе версии и реальным маршрутам.

## 10. Фиксация плана и правило завершения работы

В рамках текущего запроса: перепроверка данных → независимый Claude review → разбор замечаний и корректировка → фиксация документов в Git. Не начинать N1–N8 автоматически из факта фиксации плана. Пользовательские исходные изменения остаются вне документационного коммита; push/install/release не выполняются.

Ревью получает ограниченный пакет: этот план, утверждённые пользовательские ограничения, реестр проблем и проверенные исходные фрагменты. Claude не правит проект, не запускает других агентов и не использует secrets. Точное содержимое кандидата связывается SHA-256 с результатом; ответ сохраняется отдельно от controller acceptance. Замечания принимаются по доказательствам, а не по авторитету модели.

После разбора замечаний статус плана обновляется; решения и остаточные ограничения фиксируются в отдельном отчёте ревью. Реализация принимается только после соответствующих N-stage checks; никакой документ или положительный вердикт Claude не объявляет CENTURION 3.0 готовой системой.
